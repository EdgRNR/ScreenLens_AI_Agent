# ScreenLens WinUI 通知与布局优化阶段计划书

> 阶段：第六阶段——通知浮层、内容区布局与前端回归验收  
> 状态：待 AI 执行  
> 范围：只修改 WinUI 前端，不接入 Python、OCR、真实截图、翻译 API 或系统快捷键。

## 1. 阶段目标

修复通知出现时页面整体下移的问题，并按用户偏好适度加宽设置内容：**保持左对齐，不居中**。随后统一检查主设置窗口、通知、主题切换和截图 / 结果演示窗口，确保布局稳定、控件可见、交互提示准确；同时将应用内品牌标识统一替换为用户提供的正式 Logo。

## 2. 当前检查结果

- 当前 `MainWindow.xaml` 将根布局分为顶部 `Auto` 行和下方 `*` 行；`ToastBar` 位于顶部行，`NavigationView` 位于下方行。通知打开时顶部行增高，导航和页面内容被向下推；关闭后页面又跳回原位。
- 所有设置页目前使用约 `780` 的 `MaxWidth` 并靠左排列。大窗口 / 高分辨率下可适当增加内容宽度，但仍保持左对齐，不把设置卡片居中放置。
- 上一阶段已实现的 `SettingCard` 操作控件槽、初始导航状态、选区确认文案、主题强调色与卡片密度等功能，执行前应重新检查并保留已完成部分，不要回退。
- 当前项目默认构建未指定架构时失败，提示 `WindowsAppSDKSelfContained requires a supported Windows architecture`；指定 `x64` 和 `win-x64` 后构建成功（0 警告、0 错误）。后续本机调试 / 验收应明确使用 x64。
- 本次已启动 WinUI 程序进程；由于当前检查环境没有提供可操作的原生窗口截图接口，无法在本轮完成逐页鼠标交互或采集新的运行截图。实现本阶段时必须补上实际运行界面验收。
- 工作区根目录 `logo.png` 是用户提供的正式品牌 Logo，源图为 1254×1254 方形 PNG。它是原始素材，应保留不变；需要的图标尺寸由执行 AI 从该源图生成。

## 3. 优先级任务

### P0：通知改为不影响布局的浮层

- 调整 `MainWindow.xaml` 根布局：`NavigationView` 始终占满完整客户区，不得放在依赖通知高度的下一行。
- `ToastBar` / 通知容器作为根 `Grid` 的覆盖层与主内容共用同一单元格，置于更高显示层级；通知显示和关闭不能改变导航、侧栏、页面标题、首张卡片的尺寸或位置。
- 通知仍靠右上方显示，使用合适的最大宽度和边距；保持关闭按钮可用、定时消失逻辑正常。
- 窄窗口下若右上通知会遮挡页面标题或主要控件，应缩短通知宽度、改变其锚点或收敛提示文案；不能通过推移整页来避让。
- 检查键盘焦点和点击行为：通知出现不能抢走当前控件焦点；点击通知关闭按钮只关闭通知，不触发下方页面控件。

### P0：统一使用用户提供的品牌 Logo

- 将仓库根目录的 `logo.png` 作为唯一品牌源图，检查透明背景、图形边缘和实际留白；不要重绘、替换颜色、拉伸变形或覆盖原始文件。
- 替换 WinUI 主窗口侧栏品牌区和“关于”页中的占位 / 演示标识，并检查托盘或其他前端已有品牌入口（若存在）；品牌图像都从同一源素材派生，避免新旧标识混用。
- 更新 `Package.appxmanifest` 与 `Assets/` 中实际被项目引用的应用 / 磁贴 / Store 图标，核对 `.csproj` 的资源项和打包引用。只处理当前项目真实使用的图标资源，不要无差别重命名或删除资源。
- 按 WinUI / MSIX 所需的目标尺寸与 scale / targetsize 变体生成 PNG。使用项目已有工具或常见图像工具；保持源图比例与透明度，必要时在正方形画布内留出适当安全边距，不得把方形 Logo 硬拉成横幅。
- 对宽幅启动画面等不能直接使用正方形图标的资源，使用一致的品牌图形与简洁背景合理排版；若该资源并非本阶段必要，保留原样并说明原因，不要生硬拉伸。
- 源文件继续保留为根目录 `logo.png`；生成资源放在 `winui/ScreenLens.WinUI/Assets/`，并记录资源名称与用途，避免重复复制多个不受控的“主 Logo”。
- 构建并检查打包资源引用有效；实际运行时检查侧栏、关于页、窗口 / 任务栏图标、开始菜单或包清单图标可见时均显示正确、清晰、不被裁切。若当前运行配置无法验证系统级图标，应单独标注未验证项。

### P1：适度加宽设置内容，保持左对齐

- 将各设置页重复使用的内容最大宽度从当前约 780 DIP 适度提高，建议在 **960–1040 DIP** 范围内结合卡片内容校准；不要按整块窗口宽度无限拉伸。
- `HorizontalAlignment` 继续使用 `Left`，不采用 `Center`；左侧页面起点继续对齐，形成统一纵向基线。
- 优先统一通过共享样式 / 资源设置页面最大宽度，避免逐页出现不同宽度。
- 观察通用、截图与选区、OCR 与结果、翻译、快捷键、外观和关于页面：右侧控件与长文本应更舒展，但行宽仍易阅读。
- 超宽窗口下允许内容区保留合理空白；内容仍靠左，不要求填满整个窗口。

### P1：适配较窄窗口和长表单

- 检查窗口约 900×650、当前默认窗口和最大化状态下的设置页。
- 当卡片宽度不足时，卡片操作控件可换到下一行或使用上下布局；标题 / 描述不可挤压到不可读，ComboBox、ToggleSwitch、Button 不得越界。
- 翻译配置中的 API 地址、模型和密钥字段在较窄宽度下改为纵向排列，避免固定最小宽度造成横向溢出。
- 保证窗口高度变小时右侧内容可以滚动，侧栏和通知不遮住主要操作。

### P2：统一通知与页面视觉细节

- 通知样式与深色 / 浅色主题协调，图标、标题、内容文字和关闭按钮对比清楚。
- 通知显示 / 关闭时不改变任何页面内容的测量尺寸，连续快速触发时旧通知被替换，不堆叠多条。
- 主窗口品牌区、关于页和当前项目引用的包 / 应用图标均使用用户提供的 Logo；不同尺寸清楚、比例正确、无裁切或失真，源图未被改写。
- 统一标题、分组标题、卡片间距、控件对齐和页面左右留白。
- 基于真实窗口截图检查留白。用户偏好是设置内容左对齐并适度加宽，不要改成居中布局。

## 4. 本阶段边界

- 不修改 Python 版及 `screenlens/`、`tests/`、`run.py` 等文件。
- 不接入真实截图、OCR、翻译服务、HTTP 请求、配置持久化、剪贴板、托盘、开机启动或系统级快捷键。
- 不升级 Windows App SDK / .NET 版本，不添加大型 UI 依赖。
- 保留当前 WinUI 项目和已有演示状态，除布局修复所需外不重写页面。

## 5. 实际运行验收步骤

请在 Visual Studio 或命令行用 x64 启动 WinUI 项目，逐项验证并记录结果：

1. **初始页**：窗口启动、默认选中页、左侧导航和第一屏卡片完整可见。
2. **通知浮层**：通过会触发提示的控件（如强调色切换、快捷键演示按钮）连续显示通知；确认通知出现和关闭时，导航顶部、页面标题、卡片位置没有上下跳动。
3. **通知遮挡**：在默认、窄窗口和最大化状态检查通知是否遮挡页面标题或操作控件；通知关闭按钮可独立工作。
4. **所有设置页**：逐项切换七个导航页，检查选中态、卡片操作槽、表单换行、长文本和滚动。
5. **主题与外观**：切换深色 / 浅色 / 跟随系统、强调色和舒适 / 紧凑密度，检查窗口内资源统一且文字可读。
6. **截图演示**：打开演示窗口，拖动不同方向的选区、在边缘创建选区、调整窗口大小、确认 / 取消，再检查结果预览窗口的布局。
7. **键盘操作**：使用 Tab / Shift+Tab、Enter、Space、Esc 完成导航和关闭操作，确认通知出现时焦点不丢失。
8. 保存至少三张本阶段运行截图：设置页无通知、通知显示、窄窗口或最大化布局；截图需确认捕获的是 ScreenLens 窗口而不是整个桌面，并检查没有账号路径或其他私人信息。

## 6. 构建与运行参考

本机项目启用了 Windows App SDK 自包含部署，构建必须指定 Windows 架构。可使用：

```powershell
dotnet build winui\ScreenLens.WinUI\ScreenLens.WinUI.csproj `
  --configuration Debug `
  --no-restore `
  --verbosity minimal `
  -p:Platform=x64 `
  -p:RuntimeIdentifier=win-x64
```

在 Visual Studio 中调试时也选择 `x64` 配置。不要用不带架构的默认构建命令作为最终构建结论。

## 7. 完成标准

- 通知显示 / 关闭时，导航和页面布局稳定，没有因通知高度变化产生的整体位移或跳动。
- 通知右上显示，消息可读、可关闭、不堆叠，也不会长期遮挡主要内容。
- 设置内容比当前布局适度加宽，仍然左对齐；不同页面左右基线一致。
- 默认、窄窗口和最大化状态均无水平溢出、控件重叠、重要文案截断或不可见操作。
- 七个设置页面和两个演示窗口均完成运行检查；截图证明关键状态已实际呈现。
- x64 Debug 构建成功；汇报构建命令、运行检查清单、发现的问题和仍属演示的功能。
- 没有改动或启动 Python 版，也没有产生任何后端请求。
