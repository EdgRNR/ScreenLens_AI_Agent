> 当前状态快照：2026-09-29。后续开发与验收以本文件开头的“当前基线”和“待办”作为准绳；后面的历史计划仅用于保留决策与过程记录。

## 当前基线

- 当前桌面 UI 为 WinUI 3 / C#，项目位于 `winui/ScreenLens.WinUI/`；原 Python/Tk UI 保留为旧版原型。
- 当前开发结构为 WinUI 前端 + Python 后台 Agent + 按需 Worker，通过当前用户限定的 Windows 命名管道通信。
- Visual Studio F5 只运行 WinUI 前端；开发时需要另行启动 `.venv\Scripts\python.exe run_agent.py`。这属于开发调试方式，不等于发布版要求用户手动启动两次。
- `run_agent.py` 是当前后台代理控制台入口，`run_agent.pyw` 是无控制台入口；`run_legacy.py` 与 `run_legacy.pyw` 是旧 Tk 原型入口。
- 目前已实现前后端连接、设置读写、截图/OCR/翻译等流程；仍需要以用户实际运行和发布构建验证完整流程。
- 空闲总内存目标为所有 ScreenLens 自有进程合计 Private Working Set ≤ 50 MiB；目前目标尚未以规定的多轮测量报告证实，不能视为已验收。
- WinUI 当前视觉已基本达到用户认可水平。除修复明确缺陷外，不做大幅视觉改版。Ollama 暂不纳入近期范围。
- 当前唯一计划文件为 `docs/PLAN.md`；不再按每个阶段新增计划 Markdown。

## ScreenLens 第二阶段计划书：易用性与稳定性

> 本文件供下一轮 AI 开发直接执行。第一阶段已经交付可运行的软件；本阶段在现有 Python + Tkinter 架构上迭代，不重新创建项目。

### 1. 阶段目标

把当前“能完成截图、OCR、翻译”的原型，提升为日常使用时更容易配置、错误更容易恢复、隐私提示更清楚的 Windows 桌面工具。

优先完成三件事：

1. 用户不必手工编辑 JSON，就能更改快捷键和翻译设置。
2. 热键、OCR、翻译等后台任务不会因线程/UI 状态问题卡住或留下错误状态。
3. 设置界面和翻译流程准确说明哪些内容会联网，以及会发送什么内容。

保留现有技术栈和主流程：托盘常驻 → 快捷键截图 → 本地 OCR → 复制或按需翻译。

### 2. 当前实现检查摘要

以下结论来自现有代码和 README；请在动手前复核当前分支，若已有改动，以实际代码为准。

| 发现 | 代码位置 | 对用户的影响 |
|---|---|---|
| 快捷键配置只能通过托盘打开 `config.json` 手工编辑，没有图形设置页 | `screenlens/app.py`、`screenlens/tray.py`、`screenlens/config.py` | 普通用户难以更改快捷键或切换翻译服务 |
| 键盘库回调从工作线程启动，再调用 `root.after()` 与 Tk 主循环交互 | `screenlens/hotkey.py`、`screenlens/app.py` | 线程边界不够稳健，关窗或高频触发时可能出现 Tk 调用异常或竞态 |
| 翻译按钮没有请求中锁定；用户可重复发起请求；失败分支未统一恢复按钮状态 | `screenlens/ui/result_window.py` | 重复请求、状态提示与按钮状态不一致 |
| 翻译状态栏始终显示“文本将发送至在线服务”，即使选择 `none`；UI 也没有区分未配置与网络失败 | `screenlens/ui/result_window.py`、`screenlens/translate/provider.py` | 提示可能不准确，用户不易理解当前配置和失败原因 |
| 配置直接覆盖写入，损坏配置回退默认值但不明确提示用户，也缺少结构校验 | `screenlens/config.py` | 意外中断写入时可能留下损坏配置；无效配置难以定位 |
| OCR/翻译结果经队列更新 UI，但窗口关闭、重新截图或新任务开始后的旧结果没有任务标识 | `screenlens/ui/result_window.py` | 慢请求完成时有机会影响已经更新的界面状态 |
| README 说明混合 DPI、多显示器尚未实测 | `README.md` | 复杂显示器环境中的坐标和浮窗位置可靠性未知 |

### 3. 本阶段范围与优先级

#### P0：必须完成

##### 3.1 增加轻量设置窗口

从系统托盘增加“设置”入口。设置窗口使用现有 Tkinter，不引入新的 UI 框架。至少提供：

- 快捷键查看与修改；支持录入/捕获按键组合，并在保存前校验格式。
- 翻译提供器选择：Google 免费接口、OpenAI 兼容接口、关闭翻译。
- OpenAI 兼容配置：Base URL、API Key、模型；API Key 输入默认隐藏。
- 默认目标语言：中文、英文、日文。
- 明确说明 OCR 在本地执行；选择在线 Provider 后，用户点击翻译会把识别文本发送给该服务，截图图片不会上传。
- 保存、取消、恢复默认值；保存后立即应用，无需退出重启。
- 配置无效或快捷键注册失败时，展示可理解的错误；不要静默显示“已保存但实际未生效”。

保存快捷键时要处理注册失败：保留并恢复先前可用的快捷键/配置，向用户说明失败原因。若无法可靠判断快捷键冲突，不要宣称已检测所有冲突。

##### 3.2 加固异步任务与窗口生命周期

- 将后台任务结果统一通过线程安全队列交给 Tk 主线程处理；Tk 控件及 Tk 调度 API 只由主线程调用。
- 为 OCR 和翻译任务管理界面生命周期/任务编号。关闭结果窗、重新截图或开始新一轮任务后，旧结果不得覆盖新界面。
- 同一结果窗的翻译请求进行中时禁用重复提交；成功、失败、关闭和取消等路径都要恢复正确状态。
- 对 OCR/翻译线程中预期异常和未预期异常均给用户明确、简短的错误反馈，同时保留诊断日志；日志不得包含 API Key 或完整识别文本。
- 退出应用时停止热键、托盘和轮询任务，不从已销毁的 Tk 根窗口继续安排回调。

##### 3.3 修正隐私和状态反馈

- 根据实际 Provider 显示准确的翻译提示：在线 Provider 说明服务名称及“仅发送文本”；`none` 显示“翻译未启用/请在设置中选择服务”，不能显示成正在联网。
- 如果用户未配置 OpenAI Provider，明确引导到设置窗口，而不是要求直接编辑配置文件。
- 翻译中、成功、未配置、网络失败、服务响应错误使用一致的状态与按钮反馈。
- 截图和 OCR 不上传；除非用户点击翻译，否则不得发送内容到网络。不要新增后台自动翻译或遥测。

##### 3.4 配置可靠性

- 保存配置时采用同目录临时文件加替换的原子写入方式，并保证 UTF-8。
- 校验 JSON 根节点、字段类型、Provider、目标语言、快捷键和 URL 等必要字段；对未知/损坏配置给出可理解反馈，并避免应用崩溃。
- 保留现有配置兼容性：没有新增字段的旧配置应能自动补齐默认值。
- API Key 不得写入日志或错误提示。不要在 README、测试数据或提交文件中放真实凭据。

#### P1：本阶段完成 P0 且时间允许时

- 改善结果浮窗：翻译中禁用按钮并提供可见进度；长文本可滚动；窗口打开位置及拖动后不应跑出当前虚拟桌面边界。
- 增加“复制译文”更清楚的按钮反馈；剪贴板失败时提示用户，而不是假设复制成功。
- 建立轻量 OCR 历史（可关闭、默认仅本地），包含识别文本和时间；明确提供清空历史入口。若实现会明显扩大范围，先不做历史功能。
- 补充多显示器和混合 DPI 的手动验收记录；若环境无法覆盖，记录未验证项和复现步骤，不得写成已验证。

### 4. 本阶段不做

- 不更换 Python/Tkinter 技术栈，不重写第一阶段已有的截图/OCR 主链路。
- 不增加云端视觉识别、AI 总结、代码解释、公式识别、插件系统或多模型编排。
- 不默认上传截图、OCR 文本或使用遥测。
- 不把 OCR 历史、开机自启作为 P0；历史仅按 P1 条件考虑。
- 不为“支持更多服务”而新增没有实际测试或清晰配置说明的 Provider。

### 5. 验收标准

完成前必须按以下标准实现并验证：

1. 程序可启动并常驻托盘；托盘能打开设置、截图和退出。
2. 设置中修改快捷键并保存后立即生效；无效快捷键不会覆盖原先可用配置，并能看到错误原因。
3. 修改翻译 Provider、API 配置和默认语言后，无需重启即可在结果窗生效；取消操作不保存更改。
4. 选择 `none` 时不会出现“发送到在线服务”的提示；点击翻译能解释翻译未启用。
5. 在线翻译时先明确说明会发送识别文本；截图图像不会被发送。翻译请求期间按钮不可重复提交。
6. 模拟或制造网络失败、无效响应、未配置服务、OCR 初始化/识别错误时，应用不崩溃，界面可继续使用。
7. 在请求进行中关闭浮窗、重新截图或退出应用，不出现旧结果写入新窗口或 Tk 销毁后回调异常。
8. 配置保存后可重新读取；旧版部分配置可正常补齐；损坏配置有明确、可恢复的处理方式。
9. 复制原文/译文成功时给出确认；剪贴板异常时显示失败状态。
10. 更新 README：设置入口、配置迁移、隐私与联网行为、实际测试结果、尚未覆盖的 DPI/显示器场景。

### 6. 测试与验收方式

在完成实现后，Agent 应自行运行适用的自动化测试并增补覆盖，不得只报告“代码已写完”。优先复用现有 `tests/`：

- 配置：默认值、旧配置合并、无效字段、损坏文件、原子保存。

- 设置 UI：保存、取消、字段校验和设置实时生效。
- 翻译：Provider 状态提示、请求中防重复、网络错误、未配置、旧任务结果丢弃。
- OCR/结果窗：错误反馈、关闭/重截图后的任务生命周期。
- 回归现有矩形/自由圈选、OCR、复制、托盘启动与退出。

在线服务测试应使用 Mock 或本地假服务；自动化测试不得依赖真实 API Key，也不应要求每次测试访问真实翻译服务。至少进行一次实际 Windows 手动验收并记录操作步骤和结果。若受运行环境限制无法验证某项，明确标为“未验证”，不要推断通过。

## ScreenLens — AI 自主开发任务书

### 1. 项目定位

开发一款 Windows 桌面端轻量工具。

核心目标：

> 用户通过全局快捷键呼出工具，在屏幕上自由圈选任意不规则区域，截取该区域内容，并自动识别其中的文字；用户可以立即复制文字或进行翻译。

第一阶段重点不是做“大而全”的 AI 助手，而是把：

**自由截图 → OCR → 翻译**

这条核心链路做到稳定、快速、自然。

- 项目代号：`ScreenLens`
- 目标平台：Windows 10 / Windows 11
- 产品形态：常驻后台的轻量桌面工具
- 开发原则：由 Agent 自主选择技术栈、实现方式和工程结构，不要求人工逐步指导代码实现

---

### 2. 产品愿景

ScreenLens 是一个“屏幕内容理解入口”。

用户看到屏幕上的任何内容，不需要复制、切换窗口或手动截图，只需要：

1. 呼出工具
2. 圈选内容
3. 自动识别
4. 复制 / 翻译

未来可以在此基础上扩展：

- AI 解释
- AI 总结
- 代码识别与解释
- 数学公式识别
- 图片内容理解
- 多语言翻译
- 本地小模型
- 云端大模型
- 插件系统

这些属于未来扩展，本阶段不要为了它们过度设计。

## 4. 核心功能

### 4.1 全局快捷键

程序启动后常驻后台。

用户可以通过全局快捷键启动截图。

要求：

- 即使当前正在使用其他应用，也可以呼出
- 快捷键不要与常见系统快捷键冲突
- 快捷键最好允许未来配置
- 截图完成后自动退出截图模式

如果默认快捷键无法合理实现，由 Agent 自行选择一个合理方案，并在 README 中说明。

---

### 4.2 截图模式

进入截图模式后：

- 当前屏幕出现轻微暗色遮罩
- 鼠标操作区域保持清晰
- 鼠标指针应该清楚可见
- 显示当前选区
- 显示操作提示，但不要过度干扰

截图工具应该尽量做到：

> 用户第一次使用就知道怎么操作。

---

## 5. 自由形状截图

这是本项目最重要的特色之一。

不要只实现普通矩形截图。

至少支持：

#### 模式 A：矩形截图

鼠标按下并拖动，形成矩形区域。

#### 模式 B：自由形状截图

用户可以按住鼠标并自由绘制闭合区域，例如：

- 圆形
- 椭圆
- 任意曲线
- 不规则多边形
- 手绘圈选

例如用户看到一句话，只需要：

“圈一下这句话”

而不是必须精确拖出一个矩形。

---

### 5.1 自由形状区域处理

需要注意：

OCR 引擎通常处理的是矩形图片，因此自由形状区域可以：

1. 根据用户绘制路径计算最小包围矩形
2. 截取包围矩形
3. 将路径之外的区域设置为透明或背景遮罩
4. 再送入 OCR

实际实现方式由 Agent 自行决定。

重点是：

**用户感知到的是“自由圈选”，而不是普通矩形截图。**

---

## 6. OCR

OCR 是核心功能。

第一阶段要求：

- 支持中文
- 支持英文
- 支持中英文混合
- 尽量支持日文
- 自动识别文字方向和基本布局
- 对常见网页、聊天窗口、软件界面文字具有较好的识别效果

### OCR 架构要求

优先考虑：

> 本地 OCR

原因：

- 速度快
- 隐私更好
- 不依赖网络
- 成本低
- 可以离线工作

## 历史文件：ScreenLens_UI_交互调研与改版建议.md

## ScreenLens UI 与截图交互调研建议

> 目的：供产品确认下一阶段的界面方向，再作为后续 AI 开发任务书的基础。本文件只做调研与方案，不要求直接照抄第三方代码或视觉素材。

### 1. 结论摘要

当前 ScreenLens 的主要短板确实在 UI：程序功能入口能用，但截图操作方式藏在提示文字和 Ctrl/右键组合里；结果窗把原文、翻译、设置项压在较小的 Tkinter 浮窗中，视觉层级和操作反馈都比较像传统小工具。

建议下一阶段将 UI 目标改为：**Windows 11 风格的轻量屏幕取词工具**。保留“快捷键 → 选区 → OCR → 原文/翻译”的短流程，不添加完整截图编辑器。

建议优先参考：

- **Flameshot** 的截图选区内工具条和快捷键反馈：用户选中区域后，保存、复制、取消等动作靠近当前工作区；快捷键可完成移动、微调、复制和撤销。[官方项目说明](https://github.com/Flameshot-org/flameshot)
- **ShareX** 的区域选择与完成后动作：矩形、椭圆、自由形状明确区分；选区结束后进入明确的下一步任务。[区域截图文档](https://getsharex.com/docs/region-capture) [图像编辑器文档](https://getsharex.com/docs/image-editor)
- **Greenshot** 的易学选区细节：十字光标、窗口/区域切换、Shift 比例约束、方向键精调和放大镜。[官方帮助](https://getgreenshot.org/help/)

这些项目的共同经验是：截图时让模式、范围和可执行动作清晰可见。ScreenLens 可以吸收这些交互原则，但不需要吸收它们丰富的标注、上传、录屏和工作流功能。

### 2. 现有界面检查

以下是从当前代码得到的观察，不是对实际运行截图的视觉验收：

| 界面 | 当前实现 | 用户感受上的问题 |
|---|---|---|
| 截图遮罩 | 整屏暗化，底部单行文字说明“左键矩形、Ctrl/右键自由圈选” | 功能依赖记住隐藏手势；没有明显的模式选择控件，也没有尺寸/位置反馈 |
| 结果浮窗 | 深色无边框窗口，自绘 Label 按钮、文本框、下拉框 | 控件像临时拼装；操作层级不清；翻译后窗口直接变高，结果流缺少明确的原文/译文切换关系 |
| 设置窗口 | LabelFrame、Radiobutton、Entry 的自绘深色组合 | 与 Windows 常见设置体验差异明显；项目配置项和说明较拥挤 |
| 全局视觉 | 各窗口分别定义颜色和字体；按钮主要靠文字与颜色区分 | 缺少统一的间距、控件状态、图标和反馈规则 |

对应代码主要在 `screenlens/capture/overlay.py`、`screenlens/ui/result_window.py`、`screenlens/ui/settings_window.py`。

### 3. 开源项目的交互观察

#### Flameshot：动作贴近选区

Flameshot 在选区流程中直接提供工具与动作，并用键盘快捷键支持复制、保存、移动、调整、撤销和取消。它还允许显示/隐藏工具侧栏。适合借鉴“正在截图时，操作就出现在截图场景里”这一点。ScreenLens 可只保留少量与取词有关的动作，避免工具条塞满画图工具。

#### ShareX：任务流程清楚，但产品范围很大

ShareX 支持矩形、椭圆和自由选区；完成区域选择后可进入复制、OCR、编辑、保存等配置好的后续任务。图像编辑器本身提供大量标注和隐私遮挡工具。ScreenLens 可借鉴“选择模式显式化”和“选区结束后明确下一步”，不建议实现完整编辑器或上传任务系统。

#### Greenshot：常用操作可学、精调有键盘路径

Greenshot 区域选择使用十字光标与可见选区，也支持切换窗口选择、用 Shift 固定比例、方向键微调，以及放大镜辅助精确选择。ScreenLens 值得借鉴十字光标和可选放大镜；方向键微调可作为后续增强，不应妨碍最常用的拖动圈选。

### 4. 建议的 ScreenLens 目标交互

#### 4.1 截图状态

保留全屏冻结与遮罩，但把操作提示改为清晰的轻量浮动工具条：

- 工具条显示两个直接可选的模式：**矩形**、**自由圈选**。第一次打开默认矩形。
- 仍可保留快捷键作为熟练用户的快捷入口；不要把“Ctrl+拖动 / 右键拖动”作为唯一的自由圈选方式。
- 选区绘制时显示清楚的边框和尺寸；自由圈选继续显示路径轮廓。
- 工具条避让当前选区和屏幕边缘。空闲时弱化，开始绘制后强化反馈。
- `Enter` 完成选区，`Esc` 取消；小选区时保留当前遮罩并提示重试。
- 可选放大镜作为 P1，避免第一版改版增加复杂度。

#### 4.2 OCR 结果状态

建议将结果浮窗改为更稳定的内容面板，而不是围绕原来的固定高度窗口继续堆控件：

- 顶部简洁标题区：识别完成状态、关闭按钮；窗口可拖动。
- 主体清楚区分“识别文本”和“翻译”。识别文本保留可编辑能力。
- 首要动作突出“复制”；翻译目标语言与翻译按钮相邻。
- 翻译后在同一窗口展示译文，可滚动，提供明确的“复制译文”动作。
- 识别中、翻译中、空结果、失败、复制成功等状态使用统一的提示样式；请求中按钮禁用。
- 用户关闭、Esc、重新截图等行为保持快捷、可预期。

#### 4.3 设置状态

- 使用分组卡片和清晰标题，主要分为“快捷键”“翻译服务”“隐私”。
- Provider 选择后只显示相关输入项；密钥默认隐藏。
- 保存成功/失败后在当前窗口给出明确反馈；不要只依赖托盘通知。
- 设置页优先用简短说明与字段提示，完整技术细节留给 README。

### 5. 视觉方向

建议采用清爽的 Windows 桌面视觉，不复制任一产品的皮肤：

- 背景：中性浅色或深色面板，避免全窗口纯黑；设置页优先跟随系统主题，结果浮窗保持足够对比度。
- 强调色：保留 ScreenLens 蓝色作为唯一主强调色；错误、成功、辅助信息分别使用有语义的颜色。
- 字体：优先使用系统 UI 字体；层级区分标题、正文、辅助提示，避免所有控件都使用同一字号/粗体。
- 控件：使用一致的按钮高度、圆角、间距、禁用/悬停/按下状态；重要操作带图标和文字，不用含义不明的纯图标。
- 动效：仅用短淡入/淡出和轻量状态变化；截图遮罩和 OCR 流程不等待动画。
- 可访问性：键盘可达、焦点清楚、文字对比足够；不能只用颜色传达状态。

### 6. UI 框架建议

用户感受到的“老旧”不只由 Python 决定，也和控件、间距、层级、状态反馈有关。换框架本身不会自动解决交互问题。

建议后续 AI 在实现前先做一个很小的技术判断：

1. 评估现有 Tkinter 是否能通过统一控件样式和布局达到目标外观。
2. 若 Tkinter 对圆角、原生高 DPI、多窗口布局或一致控件状态造成明显限制，再比较 PySide6/Qt 的改造收益、打包体积、构建时间和维护成本。
3. 若决定换框架，只替换 UI 层；截图、OCR、翻译和配置逻辑尽量保留，通过清晰接口复用。
4. 先完成截图工具条、结果面板、设置页这三个关键界面的可运行原型，再决定是否迁移全量 UI。

此方案不预先要求更换 Tkinter，也不把“保持 Tkinter”当成硬性限制。是否迁移应由可运行原型和打包验证决定。

### 7. 执行记录（2026-09-28 实施）

#### 问题一：设置卡片内容缺失，控件像脱离所属设置

**根因**：`SettingCard` 是 `UserControl`。WinUI 把 UserControl 的 XAML 根元素（`Border` → `Grid` → 图标/标题/说明/内容槽）作为它的 `Content`；而页面里写成

```xml
<controls:SettingCard Icon="…" Title="…">
    <ComboBox … />
</controls:SettingCard>
```

时，`ComboBox` 又被 XAML 解析器赋给同一个 `Content` 属性，**直接把整张卡片的视觉树替换掉了**。结果只剩内部控件单独显示，边框、图标、标题、描述全部消失——与截图完全一致。

**修复**：给 `SettingCard` 加 `[ContentProperty(nameof(ActionContent))]` 并把 XAML 子元素重定向到新的 `ActionContent` 依赖属性，卡片内部的 `ContentPresenter` 绑定该属性。

- `Controls/SettingCard.xaml(.cs)` ✎：新增 `ActionContent` DP；`ContentPresenter` 由 `{Binding Content, ElementName=CardHost}` 改为 `{x:Bind ActionContent}`；加 `[ContentProperty]`。
- 七个设置页 + 快捷键页的 `DataTemplate` **用法零改动**（仍直接写子元素），全部一次性恢复正常。

**验证**：`docs/screenshots/` 下七个页面的实际运行截图（`…_General/_Capture/_Ocr/_Translate/_Hotkeys/_Appearance/_About`）均显示完整卡片：图标 + 标题 + 说明 + 右侧操作控件同行；「启动后最小化」禁用态清晰可见；不再有孤立开关或按钮。

#### 问题二：关于页品牌区 Logo 未显示、位置与左侧基线不一致

**根因（两层）**：

1. **资源 URI 解析基准错误**。`Assets/BrandLogo.png` 是相对 URI，解析基准是**引用它的 XAML 文件所在目录**。`MainWindow.xaml` 在项目根，能解析到 `Assets/…`；而 `Views/Settings/AboutPage.xaml` 会解析成 `Views/Settings/Assets/BrandLogo.png` → 加载失败。图片虽加载失败但仍占宽 56 DIP，把产品名与副标题整体向右推，于是出现"品牌区明显右移"。
2. **Assets 未部署到应用目录**。构建只把资源写进 `bin\…\win-x64\AppX\Assets\`，exe 同级目录没有 `Assets\`；未打包运行时的 XAML 资源以应用目录为基准，即便 URI 正确也会加载失败。

**修复**：

- `Views/Settings/AboutPage.xaml` ✎、`MainWindow.xaml` ✎：改用绝对 URI `ms-appx:///Assets/BrandLogo.png`。
- `ScreenLens.WinUI.csproj` ✎：新增 `<Content Update="Assets\**" CopyToOutputDirectory="PreserveNewest" />`，让 Assets 同时部署到 exe 同级目录（构建后已确认 `win-x64\Assets\` 存在）。
- `AboutPage.xaml` ✎：品牌组按内容左侧基线排列（Logo 56 DIP 正方形，`Spacing=14`，`Margin="0,4,0,20"`），不再居中悬浮。

**验证**：`ScreenLens设置_About_phase7.png`（深色）与 `ScreenLens设置_About_light_phase7.png`（浅色）中 Logo 清晰可见，品牌组左边缘与「关于」页面标题、卡片左边缘在同一条基线上。

#### 问题三：任务栏及应用图标的视觉尺寸明显偏小

**根因**：源图 `logo.png`（1254×1254）的实际图形只占画布约 69%（有效包围盒 871×863，起于 (192,195)），而原生成脚本在缩放后**又叠加了 8% 安全边距**，两层留白导致图形在图标内只有 ~64%。此外 `.csproj` 从未声明 `ApplicationIcon`，窗口/任务栏图标链路不完整。

**修复**：

- `scripts/generate_icons.py` ✎：先按 alpha 阈值裁掉透明边距并补成正方形（避免边缘极淡噪点让 `getbbox()` 形同虚设），再按用途分级留白——≤32px 任务栏/标题栏图标 0%、≤48px 2%、其余 4%；新增多尺寸 `ScreenLens.ico`（16/20/24/32/40/48/64/128/256，每个尺寸独立渲染）。

## ScreenLens WinUI 前端阶段计划书

> 阶段：第四阶段——WinUI 前端原型  
> 状态：已完成（2026-09-27，编译通过、应用可启动，待人工逐页验收）  
> 范围：只完成前端界面与演示交互，不接入 Python、OCR、截图或翻译后端。

### 1. 阶段目标

在现有 WinUI 3 项目中完成 ScreenLens 的现代 Windows 桌面 UI 原型。重点解决旧版 Tkinter 界面的视觉陈旧感，形成一套统一、易读、便于后续接入功能的界面结构。

本阶段结束时，用户应能启动 WinUI 程序，在设置页之间切换，操作演示用的开关、下拉框和按钮，并查看截图选区与识别结果的静态/模拟预览。所有交互只在当前进程内改变演示状态。

### 2. 项目现状与边界

- 已创建 WinUI 3 C# 项目：`winui/ScreenLens.WinUI/ScreenLens.WinUI.slnx`。
- 当前项目使用单项目打包模板；项目目标框架和 Windows App SDK 以现有 `.csproj` 为准，本阶段不要擅自升级 SDK 或重建项目。
- 原有 Python 应用仍在仓库根目录和 `screenlens/` 中，是独立的现有程序。本阶段不得移动、删除或修改它。
- 本阶段只修改 `winui/ScreenLens.WinUI/` 下的前端项目，以及必要时更新本文档；不得改动 Python 后端代码。
- 目标是 Windows 桌面 UI，不要求本阶段实现跨平台。

### 3. 设计参考与原则

主要参考用户提供的 Lyricify 设置页截图和 [WXRIW/Lyricify-App](https://github.com/WXRIW/Lyricify-App)：

- 固定的左侧导航，当前页有明显选中态。
- 右侧内容区有清晰页面标题，设置项按卡片分组。
- 每项设置将图标、名称、简短说明和操作控件排在同一行。
- 深色中性色为主，蓝色作为少量强调色；文字层级清楚、留白充足。
- 窗口大小变化时内容可滚动，卡片和控件不互相遮挡。

这是布局和交互的参考，不复制 Lyricify 的品牌、图标、文案或专有素材。ScreenLens 应保留自己的名称和图标，并采用 WinUI 自带控件与 Fluent 图标字形。

#### 3.1 ScreenLens 视觉基线

- 默认主题：深色；同时提供“跟随系统 / 浅色 / 深色”主题选择，并在原型进程内即时预览。
- 颜色建议：窗口底色为深灰黑，侧栏略深，卡片比内容区亮一档，正文为近白色，说明文字为中灰，ScreenLens 蓝色用于当前导航、主按钮和焦点状态。
- 使用系统字体（Segoe UI），中文优先保证字重和字号易读。
- 以 8 px 间距节奏组织布局；卡片圆角适度，边框和阴影克制。
- 保留标准 Windows 标题栏与窗口操作；不为追求仿制效果而自绘标题栏。
- 复用项目当前的 Mica 窗口背景设置；主要内容表面使用稳定的实色，避免透明材质降低文字对比度。
- 不引入 WebView、Electron、第三方 UI 套件或额外 NuGet 控件库。

### 4. 本阶段实现范围

#### 4.1 主设置窗口

主窗口作为本阶段的主要展示界面，包含左侧导航和右侧可滚动内容区。导航页面控制在以下七项，避免做成过度复杂的控制台：

1. **通用**：主题模式、开机启动演示开关、启动后最小化演示开关。
2. **截图与选区**：默认选区模式、松开鼠标后确认演示开关、选区工具条行为说明。
3. **OCR 与结果**：结果面板位置、原文字号、复制按钮外观预览、示例识别文本。
4. **翻译**：目标语言、服务商下拉框、API 地址 / 模型 / 密钥输入框的视觉样式。
5. **快捷键**：快捷键列表和“编辑”按钮的演示状态；不注册系统热键。
6. **外观**：主题选择、强调色预览、卡片密度或字号选项（只保留能清楚展示的项目）。
7. **关于**：ScreenLens 名称、原型版本号、项目说明和开源项目链接占位。

翻译设置只展示表单，不校验或保存真实凭据；密钥输入默认遮蔽。页面可以显示“原型界面，尚未连接翻译服务”的说明。

#### 4.2 截图选区演示窗口

- 使用 XAML 绘制的虚构桌面背景或内置示例画面作为底图，不截取用户真实桌面。
- 展示全屏暗色遮罩、矩形选区边框、尺寸标签和浮动工具条。
- 矩形 / 自由圈选入口、确认、取消等控件可以切换演示状态。
- 点确认后打开结果预览窗口并显示固定样例文本；不调用 OCR。
- 支持 Esc 关闭演示窗口；不要注册全局快捷键。

#### 4.3 识别结果演示窗口

- 展示原文卡片、译文卡片、状态标签和复制 / 翻译 / 重新截图等按钮。
- 内容使用明确标注的静态样例，不冒充真实识别或翻译结果。
- 按钮只更新本地演示状态或显示轻量提示；不访问剪贴板、不发送网络请求。

### 5. 前端交互要求

- 左侧导航可以切换全部页面，选中态始终与当前内容一致。
- 开关、下拉框、单选项和滑块等控件可以在 UI 中操作，并即时反映当前值；值只保存在内存中。
- 对尚未实现的操作给出明确、简短的“原型演示，尚未接入功能”提示，不出现无反馈按钮。
- 键盘 Tab 顺序合理；按钮和导航项有可见焦点；Enter / Space 可操作标准控件，Esc 可关闭演示窗口。
- 窄窗口或窗口高度不足时，右侧内容滚动，左侧导航仍可访问；不得出现控件被窗口裁切或文字覆盖。
- 不增加无意义的动画、动态背景或大量装饰图标。

### 6. 建议项目结构

保留模板生成的 `App.xaml`、`App.xaml.cs`、`MainWindow.xaml`、`MainWindow.xaml.cs` 和清单文件；新界面按职责增量组织：

```text
winui/ScreenLens.WinUI/
├── App.xaml                         # 应用级主题资源
├── MainWindow.xaml                  # 设置主窗口外壳 / 导航
```

## ScreenLens WinUI 前端修复与界面优化阶段计划书

开始修改前，先检查当前 WinUI 项目和工作区状态。以下是上一轮静态检查发现的问题，**先确认它们是否仍存在**；如果已经修复，保留现有实现并转去处理剩余事项：

## ScreenLens WinUI 前后端集成与低内存优化阶段计划书

> 阶段：WinUI 第九阶段  
> 范围：让 WinUI 成为正式前端，接入现有 Python 截图识别与翻译能力；以“后台未激活时总内存尽量低”为核心架构约束。  
> 执行方式：本阶段按本文逐项实施并验收；不要只提交分析或代码片段。除本计划外，不新增阶段说明类 Markdown 文件。

### 1. 目标与当前基线

当前仓库有两套尚未连接的程序：

- `screenlens/`：可运行的 Python 程序，已经实现托盘、全局热键、屏幕截图与选区、RapidOCR、翻译服务和 JSON 配置。现有主程序把 Tk 窗口、托盘、热键和业务调用耦合在一起；`ScreenLensApp.__init__` 还会立即启动 OCR 预热线程。
- `winui/ScreenLens.WinUI/`：WinUI 3 前端原型，设置页、截图与结果窗口目前主要是演示状态，尚未连接 Python，也未持久化设置。

本阶段交付后，用户日常只看到 WinUI 界面；Python 负责后台业务与本地服务，不再弹出第二套 Tk 设置、截图或结果界面。截图、OCR、翻译、热键和设置要有明确的前后端边界，错误与取消状态也要能正确返回前端。

### 2. 内存目标（本阶段最高优先级）

#### 2.1 空闲状态定义与验收目标

“后台未激活”定义为：ScreenLens 已启动并可从托盘或全局热键唤起；WinUI 窗口、截图选区、结果窗口均已关闭；没有 OCR / 翻译任务执行；进程进入稳定空闲状态。

- **目标：上述空闲状态下 ScreenLens 所有自有进程的 Private Working Set 合计不高于 50 MiB。** 25–35 MiB 作为努力目标，不得为了追求这个数字牺牲热键、托盘可靠性或造成频繁崩溃重启。
- 用户正在查看设置、截图或结果时，以及 OCR / 翻译正在处理时，允许内存暂时升高；操作结束后必须回落到空闲目标。
- 空闲目标不把“隐藏但仍驻留的 WinUI 窗口”视作合格方案。WinUI 关闭或退出后，窗口和前端进程必须真正释放；后台代理仍能响应托盘与热键。
- 禁止仅调用 `EmptyWorkingSet`、GC 或类似接口把工作集页面挤出 RAM 来伪造达标。必须同时记录 Private Bytes / Commit，确认没有把内存压力转嫁给分页文件或积累未释放对象。

#### 2.2 基线与测试方法

在改动前先测当前 Python 程序与 WinUI 程序，分别记录启动后、稳定空闲、打开设置、首轮截图 / OCR、操作完成后回落的进程名、进程数、Private Working Set、Private Bytes 和采样时间。区分 WinUI、Python 主程序及子进程，不得只报单个进程。

验收采样至少执行 3 次冷启动：等待进入空闲 2 分钟后连续采样 30 秒，记录均值和峰值；OCR 完成并关闭结果窗口后，观察是否在 30 秒内回到空闲目标。报告操作系统版本、构建类型、DPI、测试机器内存和测量工具。若目标未达成，提供进程级数据与下一步架构选项，不得声称“优化完成”或自行降低 50 MiB 指标。

### 3. 推荐运行架构

采用“轻量后台代理 + 按需 WinUI 前端 + 按需工作进程”的进程边界，先测基线再验证实际成本：

1. **后台代理（Python）**：仅负责托盘、全局热键、配置读写、前端唤起和本地 IPC。重构为无 Tk 的 headless 入口；空闲时不得创建 Tk 主窗口、加载 WinUI、导入 / 初始化 RapidOCR 或预热模型。
2. **WinUI 前端（C#）**：仅在用户打开设置或触发截图时启动；负责设置、真实截图选区 UI、结果展示、复制交互和用户反馈。所有窗口关闭后退出前端进程，不能为托盘或热键而让 WinUI 隐藏驻留。
3. **OCR / 翻译工作进程（Python）**：仅在收到实际任务后启动。OCR 模型延迟初始化，不在后台代理启动时加载；任务结束后释放图像和识别结果。若模型 / onnxruntime 会令常驻代理超出 50 MiB，使用独立短生命周期 worker 并在任务完成后退出，确保重内存由进程退出回收。翻译任务使用相同生命周期边界或经测量证明轻量后复用代理。

IPC 优先使用限定为当前用户可访问的 Windows 命名管道，不监听本机 TCP 端口。协议须有版本号、请求 ID、明确的成功 / 错误结构、取消和超时行为；标准日志只写 stderr / 日志文件，stdout 不得混入诊断文本。截图图像传输需有大小上限并避免无界 Base64 多份拷贝；优先长度前缀二进制帧或其他经测量的低复制方式，不把完整屏幕截图长期落盘。若实测后需要改变该架构，先在阶段报告中说明内存数据、可靠性和代价。

### 4. 实施范围与步骤

#### P0：基线测量与接口定稿

- 画清进程生命周期、托盘 / 热键唤起流程、WinUI 前端与 Python 业务模块依赖；确认 WinUI 关闭后如何回到仅后台代理状态。
- 测量现有 Python 启动预热造成的内存成本，以及 WinUI 自包含进程本身的基线。确认 50 MiB 目标以所有 ScreenLens 子进程合计计算。
- 定义并记录 IPC 请求 / 响应 schema、版本升级策略、错误码、取消方式和进程关闭规则。至少涵盖 `GetStatus`、`GetSettings`、`SaveSettings`、`RegisterHotkey`、`RecognizeImage`、`TranslateText`、`CancelRequest` 与 `Shutdown`。
- 若只让当前 WinUI 主进程常驻就无法达到空闲目标，不要开始把 OCR 全部接进这个常驻进程；落实第 3 节的按需启动架构。

#### P1：将 Python UI 解耦为后台服务

- 抽离配置、热键、OCR、翻译的业务 API，使其不依赖 Tk 控件或 UI 回调；保留现有 `Config` 校验、原子保存和兼容旧配置行为。
- 新增 headless 后台代理入口，托盘与热键继续可用；删除启动时的 OCR 预热。后台代理不得实例化 `SettingsWindow`、`ResultWindow` 或 `CaptureOverlay`。
- 按需 worker 接收一项 OCR / 翻译任务并返回结构化结果；错误、超时、取消和 worker 崩溃均可恢复，不能遗留孤儿进程或未完成请求。
- 旧 Python 启动入口在 WinUI 集成验收通过前保持可用；不要直接删除旧 UI 或破坏已有用户配置。

#### P2：实现本地安全 IPC 与 WinUI 客户端

- 建立 Python 服务端和 C# 客户端的同版本协议；启动、首次连接、重复连接、超时、重启、异常退出、应用退出等场景均有明确处理。
- 仅允许当前用户连接命名管道；不暴露网络端口，不把 API Key、识别文本或截图内容写入日志。
- WinUI 成为设置数据的唯一编辑界面。启动时从 Python 配置读取真实值；保存时调用后端校验并原子写入；保存失败时保留编辑内容并显示可理解错误，不谎报成功。
- 现有 Python 配置优先作为唯一设置来源。把已支持字段映射到 WinUI 控件；新增主题等纯前端偏好时须独立定义向后兼容字段，不能覆盖未知配置字段。尚无真实后端能力的开机启动、窗口最小化等控件须明确标记未实现或禁用，不得继续伪装为已生效。
- 翻译设置支持当前后端已有的 `google_free`、`openai`、`none` 服务；API Key 默认遮蔽，除配置界面外不回传到日志、提示、崩溃报告或 IPC 诊断信息。

#### P3：接入真实截图、OCR、翻译与结果流程

- 将当前模拟截图窗口改为真实屏幕捕获和选区流程；由 WinUI 显示遮罩、选框、工具条和取消 / 确认反馈，不再弹出 Python Tk 截图界面。
- 选区确认后只将必要的裁剪图像交给 Python OCR worker；屏幕坐标和结果定位按 DPI / 多显示器坐标正确传递。
- 识别结果显示在 WinUI 结果窗口。复制操作使用 Windows 剪贴板 API 并给出成功 / 失败反馈；“重新截图”、取消、关闭窗口均可正确结束当前任务。
- 翻译只发送识别文本，不发送截图；用户选择关闭翻译时不创建网络请求。翻译网络错误、超时和取消有可恢复的 UI 状态。
- 全局热键由后台代理注册，按下时启动或唤起 WinUI 截图流程；设置窗口运行期间不得意外重复唤起，热键修改失败要回滚并展示原因。

#### P4：生命周期、内存和回归验收

- 验收：冷启动到托盘空闲、打开 / 关闭设置、热键截图、OCR 失败 / 成功、翻译失败 / 成功、取消任务、快速重复触发、代理 / worker 崩溃重启、系统注销或退出。
- OCR 前后检查图像缓冲、模型对象、窗口引用和任务线程；处理完毕后清理不再使用的数据。不得在前端或后台代理缓存整屏截图、历史文本或模型结果。
- 验证 WinUI 窗口关闭后前端进程退出，worker 按生命周期退出，后台代理保持可用；最终运行一整轮内存采样并对照第 2 节目标。
- 在 Debug 与最终发布配置下分别核对进程数量、IPC 行为和内存；打包流程应能启动无 Tk 的后台代理及按需 worker，不得把开发机虚拟环境路径写死。

### 5. 隐私、安全与兼容性

- OCR 保持本地运行；任何翻译请求只发送识别文本，并在 UI 中提示所选服务商和联网行为。
- 截图、识别文本、API Key 不写入日志；IPC 断开或接入失败时不得回退到无认证 HTTP 服务。
- 不把 API Key 放入命令行参数、环境变量转储、崩溃日志或持久化临时图像；设置保存继续使用既有安全写入方式。
- 默认配置、旧版 `%APPDATA%\ScreenLens\config.json`、未知字段和已有用户设置须兼容；迁移必须无损，失败时保留原文件并提供恢复说明。
- 不引入本地 Ollama、云端 OCR 或其他新服务；不要求用户配置 API Key 才能使用本地截图与 OCR。

### 6. 验收标准

1. 用户日常只使用 WinUI；托盘、全局热键、设置、截图、结果和翻译流程均真实可用，Python Tk UI 不会与 WinUI 重叠弹出。
2. 设置可以从现有 Python 配置正确读取、校验、保存和重载；错误不会造成静默丢设置。
3. 空闲状态进程级采样可复现，ScreenLens 所有后台进程合计 Private Working Set **不高于 50 MiB**；同时提交 Private Bytes 数据。OCR / 翻译任务结束后 30 秒内回到目标。
4. 操作活跃期间记录峰值及进程明细；允许高于 50 MiB，但任务结束后不能持续增长或留下 OCR worker / WinUI 窗口进程。
5. OCR、翻译和热键回归测试通过；测试翻译使用 Mock / 本地假服务，不要求真实 API Key，不发送真实用户截图或识别文本。
6. 调整窗口大小、深浅主题、100% / 150% 缩放及多显示器截图时，WinUI 页面和选区不发生遮挡、裁剪或错位。
7. WinUI x64 Debug 与项目既有发布构建均成功；报告修改文件、构建命令、测试结果、人工操作路径、进程树、空闲 / 活跃内存数据及仍未完成的项目。

### 7. 执行约束

- 先盘点和测量，再确定 IPC 与进程生命周期；不要先写桥接代码后才发现 WinUI 常驻基线已突破内存目标。
- 先建立 headless 后端和协议，再逐项接入设置、截图 / OCR、翻译；保持每一步可构建、可回归、可回退。
- 不要把“隐藏窗口”“最小化”当成释放内存；不要把窗口隐藏、GC 或清空工作集当成进程已退出。
- 不得为了达到指标取消全局热键或托盘，不得删除已有 OCR / 翻译能力，也不得破坏 Python 旧配置。
- 若完成按需进程、延迟加载和资源释放后仍无法达到 50 MiB，停止宣称阶段通过；提交真实测量和造成超标的模块，并说明达到目标所需的架构取舍，等待产品决策。

### 计划验收结论

本计划的总体方向可执行：将常驻轻量代理与按需前端/识别工作分离，并把低内存作为量化验收项。以下单实例唤起、真实进程生命周期和设置兼容要求已补入，避免只实现 IPC 请求而遗漏实际使用路径。

#### 必须明确的进程与唤起规则

1. **后台常驻态：** 仅保留轻量 Python Agent，负责托盘、全局热键、配置和 IPC；不得创建隐藏的 Tk 窗口，不得导入或预热 OCR 引擎，不得常驻持有截图位图。
2. **打开设置：** Agent 启动 WinUI 设置窗口。若窗口已存在，通过单实例激活通道切回并聚焦现有窗口，不得再创建第二个设置进程或窗口。
3. **触发截图：** 热键由 Agent 接收后，通知现有 WinUI 进程开始截图；若 UI 尚未启动则按需启动，并直接进入截图流程。截图选区、预览和结果展示统一由 WinUI 承载。
4. **关闭与回收：** 关闭最后一个 WinUI 窗口后，UI 进程应退出；Agent 继续低内存驻留。OCR/翻译任务完成后释放图像、临时文件和任务级对象，不将模型或大图像缓存留在 Agent。
5. **开发启动：** Visual Studio F5 直接启动 WinUI 时，应支持独立预览/开发模式；真实连接测试则明确使用 Agent + WinUI 双进程模式，避免开发便利逻辑混入发布生命周期。

#### 本次计划复核补充项

- IPC 协议须定义消息方向与版本：例如 `OpenSettings`、`BeginCapture`、`CaptureCompleted`、`OcrCompleted`、`Translate`、`Cancel`；有请求 ID、超时、取消、结构化错误和有界消息大小。
- IPC 使用当前用户受 ACL 保护的 Windows Named Pipe，不监听本地 TCP 端口；密钥和识别文本不得写入普通日志。截图仅发送用户选定区域，避免整屏无意外传输。
- 配置继续兼容现有 `%APPDATA%\ScreenLens\config.json`；API Key 按密钥处理（界面遮蔽、日志脱敏），对旧配置做向后兼容迁移，不因前端接入重置用户设置。
- 所有当前 UI 选项必须映射到真实后端行为，或明确标为未实现/禁用；禁止保留看似可操作但仅改变内存演示值的假开关。
- 内存验收按**整个应用进程树**统计；分别记录后台稳定态和空闲 UI 态。后台稳定态目标仍为总 Private Working Set < 50 MiB，争取 25–35 MiB；同时报告 Private Bytes 作为辅助数据，避免只看单一指标误判。
- 建议统一测量环境、预热方式和采样窗口：启动后等待稳定，再连续采样至少 60 秒，报告均值、最大值和 P95；分别运行三轮，并记录 Windows 版本、构建配置及是否启用调试器。明确允许 OS 缓存波动，但不能把 UI/OCR 进程常驻归入“后台空闲”。
- 禁止通过 `EmptyWorkingSet`、频繁强制 GC 或其他仅压低瞬时显示值的手段宣称达到目标；优化应来自进程退出、延迟加载、释放大对象与减少常驻依赖。
- 在新增代码前先盘点现有 Python 模块的 import 链、`warmup_async()` 调用点、Tk 主循环和托盘/热键所有权；重构时保留可回退路径，逐阶段验证旧 OCR/翻译功能没有回归。

**验收判断：** 原计划适合作为下一阶段基础，但仅在上述生命周期、协议、兼容和测量要求一并纳入后，才算完整可执行。计划已在本文件中补齐；后续由 Codex 按阶段直接实现与验证。

- 保证窗口高度变小时右侧内容可以滚动，侧栏和通知不遮住主要操作。
